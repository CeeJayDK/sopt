GPU-Bench / TexBench

TexBench

What texture reads, render target writes, blending and pass states cost on your graphics card.

The numbers show how expensive texture operations are next to math (when a lookup table beats computing a value, and the other way round) and how the texture formats ReShade supports really perform on your GPU.

How to run

From the GPU-Bench menu (GPU-Bench.bat): 1 runs it with the other programs, 5 alone. It takes a few minutes and writes Reports\texbench-<GPU>.csv and two pictures of the pixel order.

Command line

--listshow the graphics cards Windows reports, with their numbers
--adapter Nmeasure card number N instead of the one with the most video memory
--filter textonly tests whose name contains text (quick checks)

How a test works

TexBench runs small shaders on the GPU (Direct3D 11) and times them, like OpBench. Costs are in sopt units: 4 = one fma (multiply-add), measured as extra time over the test's base. Every texture test reads at a coordinate computed from the previous result, so the reads in one chain cannot overlap; the base computes the same coordinate without reading, so the cost is the read alone (for Load: with the conversion of the coordinate to texels). Each test is read at least twice against a fresh reference, and more often when the readings disagree. Texture reads depend a lot on caches and memory, so read the numbers as ballpark figures.

Three ways (compute shaders), as in OpBench

tput8 chains per thread, 1M threads: the GPU can overlap reads of different chains and threads. The ballpark for a read inside a real shader.
dep1 chain per thread, 1M threads: only other threads hide the waiting.
lat1 chain, one group of 64 threads: nothing hides it; close to the raw latency of a read.

The tests

Formats and filtering

1024 × 1024 with mipmaps, coherent, shown as one table. Every format ReShade supports (R8 ... RGBA32I, plus RGBA8 with an sRGB view), each with:

Loadtexel fetch, no filtering
pointSampleLevel with point filtering
bilinbilinear filtering (4 texels)
gatherGatherRed: one channel of the 4 texels a bilinear read would use
trilintrilinear: blends two mip levels (8 texels)
aniso2 .. aniso16anisotropic filtering with MaxAnisotropy 2, 4, 8 and 16, on a steep (16 × 1 texel) footprint so the setting decides how many samples are taken

Each thread reads within one texel of its own pixel, in 8 × 8 tiles, like a post-processing pass: mostly cache hits. Shows which formats are slower to filter (some GPUs filter 64-bit formats at half speed, unpack RGB10A2 / RG11B10F, or filter point and bilinear at different speeds). Integer formats cannot be filtered: Load and gather only. Formats a GPU cannot gather or mipmap are left out and listed. GB/s: the texel data the bilinear read (integer formats: Load) delivers per second at full throughput. Formats with the same texel size do not always cost the same, so this shows which formats give the most data for the time. Formats are listed from the smallest texel to the largest.

Formats: random reads from 4096 × 4096 (Load)

The same formats read at random places: cache misses, so the texel size and memory speed show (R8 = 1 byte per texel, RGBA32F = 16). Large textures in big caches (64+ MB on some GPUs) stay partly cached. The next place comes from the value read and the place before it (from the value alone, R8 with its 256 values would visit only 256 places, all in the cache).

Color lookup tables

Coherent colors (like an image), RGBA8. N = 32 and 64. The colors change smoothly over the screen, so neighbouring pixels read neighbouring LUT entries. Cost = the whole lookup (coordinates, reads, blend).

2D N (2 reads)a 3D LUT stored as N slices of N × N side by side in a 2D texture: two bilinear reads and a lerp between the slices (the way ReShade's LUT.fx does it).
3D N^3one read from a 3D texture (the hardware filters the 8 texels).

Lookup tables and texture size

RGBA8, random reads, bilinear.

LUT 256x1a 1D lookup table (1 KB): always in the cache. Compare with OpBench's math costs (pow, exp, sin ...) to see when a lookup table is cheaper than computing.
LUT 32^3a 3D color grading lookup table (128 KB), trilinear between slices.
512^2 ... 8192^2random reads from growing textures: where the caches run out.

Cache sizes

Random reads (Load) from an RGBA8 texture of 4 KB ... 256 MB in steps of 2×. While the texture fits in a cache level, reads cost about the same; where the cost jumps, a cache level ran out (clearest in the lat column: the waiting time of a single read). So the jumps show this card's cache sizes (texture / L1 cache, L2 cache, and on some AMD cards the large Infinity Cache).

Cache use

RGBA8 2048 × 2048 (Load), reads around each thread's own pixel.

spread Neach thread reads at random within N × N texels around its own pixel (N = 1 ... 256). Neighbouring threads share cache lines while N is small; the cost rises where they stop sharing. Shows how far apart neighbouring pixels may read (blur radius, sample patterns) before the cache stops helping.
row N, column Nrandom along the pixel's row / column only (N texels): a horizontal against a vertical blur pass. Equal costs mean the texture is stored in tiles.
group WxHcompute: 64 threads as W × H pixels (8x8, 16x4, 32x2, 64x1), spread 8: which thread group shape uses the cache best.

Texel size: R8, RGBA8, RGBA16F, RGBA32F random reads (Load) from 1024 × 1024: the same texel count in 1, 4, 8 and 16 MB. Shows whether bigger texels fill the caches sooner.

Render target writes

Full-screen passes into 3840 × 2160. Each format as a render target, in GB/s, written three times by the same pixel shader: noise (which cannot be compressed), a smooth gradient and one flat color. GPUs compress render targets, so compressible output can be written faster than the memory bandwidth allows; the two Gain columns (smooth / noise, flat / noise) show how well this card compresses each format. The passes alternate between two targets: some GPUs (NVIDIA among them) keep back to back full-screen draws into one target in an on-chip cache, so only the last one would reach memory. Small formats (R8, R16) are usually limited by the pixel rate (ROPs), not by memory.

Blending

Full-screen passes into 3840 × 2160 (ms per pass). ReShade passes can blend their output into the target (BlendEnable, BlendOp, SrcBlend, DestBlend) instead of reading the image in the shader. For RGBA8, RGB10A2, RG11B10F, RGBA16F and RGBA32F: a plain write, then four common blends, each done by the blend hardware ("blend") and by a shader that reads the target's content as a texture and does the same math ("shader"): add (ONE, ONE: e.g. bloom), lerp (SRCALPHA, INVSRCALPHA: mixing with the image), multiply (DESTCOLOR, ZERO) and min (BlendOp MIN). The faster of each pair is shown in green. Before each pass a plain draw restores the target's content; those draws are timed alone right before and subtracted. Two targets take turns, as for the writes.

Pixel shader order

Which pixels the GPU shades together (not a timing). One full-screen draw into 1024 × 1024. Every pixel takes the next number from one shared counter (an atomic add) and stores it at its position, so the numbers show the order in which the GPU shaded the pixels. GPUs shade pixels in 2 × 2 quads and hand them to the shader units in larger groups (waves of 32 or 64 pixels on most GPUs, 8 / 16 / 32 on Intel).

Block Npixels whose numbers fall in the same run of N (0..N-1, N..2N-1, ...). "Compact" is the share of these runs that fill a rectangle exactly (e.g. 8 × 4 for 32): such pixels were shaded together. The largest size where most runs are compact is printed below the table.
Tile Bfor squares of B × B pixels: 100% when the square got one unbroken run of numbers (the GPU finished it before moving on), lower when it was mixed with other squares.
PicturesReports\texbench-<GPU>-order.png: the whole order from blue (first) to red (last). ...-order-zoom.png: the middle 64 × 64 pixels 8× enlarged, one color per block of the size found, black lines between blocks, darker lines between 2 × 2 quads.
Countera structured buffer first (NVIDIA merges a wave's atomic adds into one and gives its pixels consecutive numbers, so runs of numbers show the waves); where that gives no numbers, a 1 × 1 texture, where every pixel takes its own turn, so the waves do not show (CSV row "counter kind").
Speedthe same draw timed plain, with the store alone and with the counter and the store. The cost per pixel over the plain draw shows what one shared counter costs when every pixel uses it (they have to take turns).

The score

Texture ratebilinear RGBA8 reads per second (GTexels/s): the whole read step, because the coordinate math runs beside the texture units when they are the limit.
Pixel fill ratethe fastest render target write, in pixels per second (GPixels/s).
Memory bandwidththe fastest write of noise (cannot be compressed), GB/s.

These are the numbers GPU spec lists give; measured ones are usually a bit lower. The CSV is written again after every section, so a run stopped early still leaves its results.
