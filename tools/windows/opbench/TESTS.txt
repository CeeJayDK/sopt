OpBench - what the tests measure
================================

Why
---
sopt rewrites small pieces of shader math into cheaper forms that give the same result. Which
form is cheaper depends on the GPU. A sign() costs one instruction on one card and seven on
another, and some cards apply saturate() or "* 2" for free. OpBench measures these costs on
real cards. The results become sopt's cost models, one per GPU family (for example NVIDIA Turing,
NVIDIA Blackwell, AMD RDNA, Intel Gen9).

How a test works
----------------
Each test is one small step, repeated thousands of times in a chain inside a compute shader:

    x = mad(f(x), c.x, c.y)

f is the operation under test, and the mad (multiply-add) keeps x in a sane range. The
constants c change at every step, so neither Microsoft's shader compiler nor the GPU driver can
fold the chain away. The shader code of every test, with fxc's DXBC output, is written to
opbench-dxbc\ so folded tests can be spotted.

The reference test is the bare step x = mad(x, c.x, c.y): one fma (fused multiply-add) per step.
Every time is divided by the reference's time and multiplied by 4, so one fma = 4 units.
A test's cost is its time minus the time of its base test. The base is the same step without the
operation under test, usually the reference itself. So "Cost 4" means the operation costs as much
as one more fma, and "Cost 0" means it is free (the GPU folds it into a neighbouring instruction).

Before every test the reference is measured again. A GPU clock change (boost, temperature,
power saving) then affects the reference and the test alike, instead of making the test look
cheaper or dearer. Every test runs twice: forward through the list, then backward. Slow drift
cancels out. When the two readings of a test disagree (by more than 0.75 units or 15%), it is
measured again, like a third sensor: two readings show that one is wrong, three or more show which
one. This repeats until more than half of the readings agree (at most 6 passes); the result is the
mean of the agreeing readings. A test without such a majority is marked "no consensus".

Three ways of running
---------------------
  Throughput        8 independent chains per thread, about a million threads. How many of an
                    instruction the GPU finishes per second. This is the number sopt uses, and
                    the summary shows it.
  Dependent chains  1 chain per thread, about a million threads. Every step waits for the one
                    before it, and the GPU hides the waiting by switching between threads.
  Latency           1 chain, one group of 64 threads. How long one step takes until its result
                    is ready, since nothing can hide the wait.
All three are in the CSV.

The tests
---------
Modifiers and folds (often free: the GPU applies them inside another instruction)
  neg, abs, negabs  -x, abs(x), -abs(x) feeding the mad: source modifiers, usually free.
  saturate          clamp to [0, 1] on the previous mad's result: an output modifier.
  satmad            saturate(mad(...)): the same, measured against two mads.
  mul               x * c before the mad: some drivers merge it into the mad.
  omod2, omodhalf   rcp(x) * 2 and * 0.5: AMD can scale a result by 2, 4 or 0.5 for free.
  omod3             rcp(x) * 3: the control (3 is no output modifier scale).

Basic arithmetic
  min, max, step    min / max / compare; NVIDIA Turing runs one of them beside an fma.
  add, sub          one add.
  mad2, contract    a second mad, and x * a + b written out (compiled to one fma?).
  max3, minmax      max(max()), min(max()): AMD has 3-operand instructions for these.
  clamp             clamp(x, a, b): AMD v_med3 does it in one instruction, others need two.
  select            x < a ? b : x: compare + select.
  lerp              lerp(a, x, t): fxc writes it as add + mad.

Rounding and sign
  floor, ceil, round, frac   the rounding instructions (quarter rate on some NVIDIA cards).
  roundadd, flooradd,        round / floor / frac built from adds with a magic constant
  fracadd                    (1.5 * 2^23), for cards where the rounding instructions are slow.
  sign              HLSL sign(): fxc writes compare, compare, int subtract, int -> float.
  signsel2, signbits, signsat, signmad, signclamp, signsel
                    other ways to get -1 / 0 / +1 (signsel2 and signbits give +1 at 0; signbits
                    copies the sign bit onto 1.0 with two integer instructions), without
                    the int -> float conversion that makes sign() slow on newer NVIDIA cards.

Division and transcendentals
  rcp, rsqrt, sqrt, exp2, log2, sin, cos   the special-function unit (1/4 or 1/8 rate on
                    most cards).
  div, divxy        c / x and x / y (rcp + mul).
  exp, log          fxc: exp2 / log2 with a multiply.
  pow               fxc: log2, mul, exp2.
  rcpmax            max(rcp(x), c): the base for the omod tests.

Vector (float2 / float3 / float4)
  mad2v, mad3v, mad4v   the reference on 2, 3 and 4 components (2, 3, 4 fmas).
  dot2, dot3, dot4      dot products. fxc writes one dp2 / dp3 / dp4 instruction, but GPUs since
                        about 2010 have no such instruction: the driver splits it into mul + fmas.
                        These show whether that is so (old VLIW cards did have a real dot).
  cross                 cross product: 3 mul + 3 fma.
  length, distance      dot, sqrt (distance: 3 subtracts first), plus one fma of the step.
  normalize             dot, rsqrt and 3 multiplies.
  reflect               i - 2 * dot(i, n) * n.

Written out by fxc (no single instruction exists; fxc emits a sequence)
  smoothstep        subtract, mul_sat, mad, 2 multiplies.
  fmod              divide, frac, compare, select, multiply.
  sincos            sin and cos of the same value (some GPUs share the work).
  tan               sin, cos and a divide.
  atan, atan2       polynomial approximations (atan2 adds quadrant fixes).
  asin, acos        polynomial with a sqrt.

Integer and conversions (chains of uint values, x = (x ^ a) * b, with random 32-bit constants)
  bitor             one integer OR on a float value: is switching between float and int free?
  ixmul             the integer base step: xor + 32-bit multiply.
  iadd, iand, imin  one more add / and / unsigned min (NVIDIA can merge and + xor into one LOP3).
  ishr              x ^ (x >> 13): shift + xor.
  irot              rotate by 7: shl, shr, or, or one funnel shift / align instruction.
  imul              a second 32-bit multiply (slower than float on some cards).
  popc, fbh         countbits, firstbithigh.
  bitrev            reversebits.
  unitf             uint -> float in [1, 2) through the bits (shift, or): a fast random-number trick.
  utof, ftou        uint -> float and float -> uint conversions.
  ftoitof           float -> int, an integer or, int -> float (fxc writes float(int(x)) alone as
                    one truncation instruction, so the or keeps the conversions).

Half precision (min16float)
  mad16, add16, mul16, rcp16, sqrt16, exp2_16   the same steps in 16-bit floats. AMD RDNA and some
                    other cards run these at twice the rate (two per instruction). Drivers may run
                    min16float at 32 bits instead. The summary and the CSV header say which.

Reading the CSV
---------------
Lines starting with '#' describe the card, driver, OpBench version and how much the reference
moved (drift) in each mode. Then one row per mode and test:
  units          the test's time in units (4 = one fma): the mean of its agreeing readings
  units_vs_base  minus its base test: the cost shown in the summary
  vs_base_fwd, vs_base_bwd   the same for the forward and the backward pass alone
  passes, consensus, readings   how many passes the test needed, whether most readings agreed,
                 and every reading (units, ';'-separated)
  step           the HLSL step, note: what it is about
